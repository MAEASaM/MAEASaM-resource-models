# Data Ingestion Workflow - Long-term Plan

How incoming data (usually Excel files from partners) should get into Arches, and how it should be edited afterwards. Written 2026-10-26. The current phase is decided; later phases are a direction, not a commitment, and should be revisited as each one becomes relevant.

## The problem this solves

- Contributors send Excel files. They know related records by name or code (a SASES code, a site name, a person's name), not by Arches `ResourceID` UUID.
- Arches' Single CSV import needs Resource-Instance fields written as a JSON object inside a CSV cell (`[{"resourceId": "...", "ontologyProperty": "...", ...}]`, see Task_List #68/#69). This is hard to write by hand, easy to break, and not human-readable.
- Once a file is converted into that format it can no longer be read or reviewed by people, and editing it by hand (often in Excel) has already caused encoding corruption (see CLAUDE.md / Task_List #39).

The root cause is that one file is being asked to be both human-readable and machine-loadable. The plan separates the two.

## Core principles

1. **Two layers, one direction.** The human layer (intake Excel) is the source a person edits. The machine layer (the file loaded into Arches) is a build artifact generated by a script and never edited by hand. Fixes are made in the human layer and the machine file is regenerated.
2. **Relations by natural key, not UUID.** Intake files reference related resources by a key people already know (e.g. Map -> Grid by SASES code, Task_List #115; Actor by MAEASaM ID or name). The pipeline resolves keys to `ResourceID`s.
3. **Deterministic ResourceIDs.** The pipeline assigns each resource a UUID derived from its natural key (e.g. `uuid5(<project namespace>, "grid:" + SASES code)`). Consequences: a related resource's ID is known before it is loaded (load order stops mattering), and re-ingesting the same record lands on the same resource instead of creating a duplicate. Related to Task_List #66 (ResourceID pre-assignment) and #44/#48 (identifier schemes) - the namespace and key per model must be decided together with those.
4. **Labels, not concept IDs.** Intake files use controlled-vocabulary labels (as dropdowns where possible); the pipeline maps them to concept IDs from `Thesaurus/xml` (which must be current - Task_List #118).
5. **Rules live in one place.** Validation reads `metadata_rules.json` and the Metadata Templates (Necessity, Cardinality, Data Type, Collection); no rule is hardcoded only in a script.
6. **After load, Arches is the source of truth.** Intake Excel files are only an entry vehicle; they are not kept in sync with Arches afterwards.

## Phase 1 - current: Excel -> Python pipeline -> Arches business-data JSON

```
[Intake Excel] -> [Validate + resolve (Python)] -> [Arches business-data JSON] -> [Arches]
      ^                     |
      +-- error report (Excel, failing cells highlighted)
```

1. **Intake Excel (.xlsx, not .csv).** One template per resource model; column headers are the Metadata Template field labels; vocabulary columns use dropdowns of labels; relations use natural keys. Geometry comes as a separate GeoPackage/GeoJSON joined by the same key, not as WKT in a cell. Using `.xlsx` avoids the Excel ANSI-codepage CSV problem entirely.
2. **Validation and resolution (`Scripts/`).** Checks required fields, cardinality, data types, EDTF dates and vocabulary membership; resolves labels -> concept IDs and natural keys -> deterministic ResourceIDs; flags unresolved keys (e.g. a SASES code with no Grid match) instead of guessing.
3. **Output.**
   - Valid input -> Arches **business-data JSON** (`resources` -> `tiles`), which carries nested tiles and Resource-Instance relations natively, with no JSON-in-CSV cells.
   - Invalid input -> an error-report Excel returned to the contributor, with the failing cells highlighted and a reason column.
   - Single CSV stays acceptable for flat models with no Resource-Instance fields.
4. **Load** with `manage.py packages -o import_business_data -s <file>.json` (or the REST API for small batches).

### Edits after load (Phase 1 CRUD)

| Operation | How |
|---|---|
| Create | New rows through the intake pipeline above |
| Read / review | Arches UI and search; exports for reporting |
| Update - single record | Arches resource editor (provisional edits / reviewer role where needed) |
| Update - bulk | Export from Arches -> script builds a readable Excel (related resources shown by name/key, `ResourceID` in a hidden locked column) -> edit -> pipeline -> re-load with the same ResourceIDs (overwrite) |
| Update - simple text fixes | Arches Bulk Data Manager string editor |
| Delete | Arches UI / Bulk Data Manager; never by direct SQL |

## Phase 2 - possible: own review interface backed by a staging database

Worth building once intake becomes regular (several partners, recurring batches) and the Phase 1 rules have stabilised.

- **Staging database** (PostgreSQL + PostGIS, separate from the Arches database): incoming batches land here, keyed by natural key and deterministic ResourceID, with batch/source/status columns and history. Enables SQL cross-checks (duplicates, orphan relations, geometry validity, coverage per country) that are awkward in files.
- **Review interface** on top of it (e.g. Streamlit or a small Django/FastAPI app): upload an intake Excel -> see validation errors -> fix or comment -> a reviewer approves -> approved records are exported as business-data JSON (or pushed via the Arches API).
- The staging DB is a holding and QA area, not a second source of truth: once records are loaded, Arches owns them, and bulk edits go through the export -> edit -> re-load path.

## Options considered

| Option | Pros | Cons | Verdict |
|---|---|---|---|
| Excel + Python pipeline + business-data JSON | No new infrastructure; contributors keep using Excel; rules stay in `metadata_rules.json` | Weak concurrency and history; errors handled by file round-trip | **Phase 1 (current)** |
| Arches Single CSV with JSON-in-cell relations | Native, already tried | Fragile, unreadable, error-prone by hand | Flat models only |
| Separate PostgreSQL/PostGIS staging DB + own review UI | SQL validation, history, geometry QA, multi-user review | A second system to build and maintain | **Phase 2 candidate** |
| DuckDB / SQLite inside the pipeline | SQL power, single file, no server | Not multi-user | Optional helper in Phase 1 |
| Writing directly into the Arches database (SQL) | Fast | Bypasses Arches validation and Elasticsearch indexing; breaks on upgrades | **Never** |
| ArcGIS (Field Maps / Survey123) | Strong field collection and geometry QA | Licence cost; no ready bridge to Arches (custom sync) | Only if field collection is needed |
| QGIS + GeoPackage | Free; good for geometry checking/editing | Clumsy for attribute entry | Geometry layer of the intake |
| KoboToolbox / ODK | Free forms, offline, dropdowns | Deeply nested models are hard to express as forms | Possible field-entry front end |
| Google Sheets instead of Excel | Shared editing, validation lists, UTF-8 safe | Depends on institutional policy | Alternative to Excel for intake |
